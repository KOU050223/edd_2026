# 入力経路の設計

Gakushu Sochi が「何を見て」答えるか、その入力をどこから取るかの方針。

実装の詳細ではなく、**なぜ今この形なのか**を残すための文書。

---

## 目指す形

[idea.md](idea.md) にある通り、Nani のように **必要なときだけ素早く呼び出せる** UX を最終目標とする。

理想は、アプリを問わず画面上のどこでも範囲選択してホットキーを押せば、その場で調べられる状態である。エディタの中に限らず、ブラウザ、PDF、チャット、ターミナルを横断する。

```text
どこかで範囲選択
↓
ホットキー
↓
その場で回答
```

**この形はOSに常駐するネイティブアプリでしか実現できない。** VS Code拡張には次の2つの制約があるためである。

| 制約                               | 意味                                                                                      |
| ---------------------------------- | ----------------------------------------------------------------------------------------- |
| グローバルホットキーを登録できない | キーバインドは VS Code にフォーカスがあるときしか発火しない                               |
| 他アプリにコピーを命令できない     | ターミナルには `workbench.action.terminal.copySelection` を送れるが、ブラウザには送れない |

どちらもAPIの不足ではなく、拡張が VS Code のプロセス内で動くことによる原理的な制約なので、工夫では回避できない。

---

## 現状の妥協

ネイティブ化は範囲が大きく、MVPの検証より先に着手すべきではない。MVPで確かめたいのは次の2点であり、どちらもネイティブ化なしで検証できる。

1. 選択して即座に聞ける体験に価値があるか
2. コピーして ChatGPT に貼るより明らかに楽か

そこで現時点では次のロジックを採る。

> **コマンドを実行した時点で、クリップボードの最新の内容を取得して送信する。**

ユーザーがコピーする手間は残る。しかし「選択した内容をその場で調べる」という体験の核は再現できる。検証したいのは体験の価値であって、コピーが1回挟まるかどうかではない。

### 操作

1. どこかで範囲選択して `Ctrl + C`
2. VS Code に切り替える
3. `Ctrl + Alt + J`（またはコマンドパレットから `Gakushu Sochi: Ask Clipboard`）
4. 確認ダイアログで内容を見て「送る」

`Ctrl + Alt + J` に `when` を付けていないのは、フォーカスがどこにあっても動かすためである。他アプリから戻った直後はフォーカス位置が予測できず、条件付きにすると意図しないコマンドが動く。

### この方式の限界

**隠さず記録しておく。** いずれもネイティブ化するまで解消しない。

| 限界             | 内容                                                                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 来歴が分からない | クリップボードに「どこから来たか」の情報はない。ブラウザ由来かどうかは判定できないため、`source` は `browser` ではなく `clipboard` とする |
| 鮮度が分からない | 「今コピーした内容」と「何時間も前の内容」を区別できない。古いパスワードが残っていても検出できない                                        |
| 付随情報がない   | URL、ページタイトル、周辺のコードは失われる                                                                                               |

鮮度の問題があるため、**送信前の確認ダイアログ（`apps/vscode-extension/src/ui/confirm.ts`）が唯一の防御になる**。この経路から確認を外してはならない。

## 入力経路の一覧

| 経路                 | コマンド                            | コピーを実行するのは | 取得できる情報                 |
| -------------------- | ----------------------------------- | -------------------- | ------------------------------ |
| エディタの選択範囲   | `gakushuSochi.askSelection`         | —                    | テキスト、ファイル、言語、位置 |
| ターミナルの選択範囲 | `gakushuSochi.askTerminalSelection` | 拡張                 | テキストのみ                   |
| クリップボード       | `gakushuSochi.askClipboard`         | **ユーザー**         | テキストのみ                   |

ターミナルとクリップボードはどちらもクリップボードを経由するが、**コピーを誰が起こすかが違う**。ターミナルは拡張がコピーを実行できるため「何も選択されていない」を目印（sentinel）で検出できる。クリップボード経路ではコピーを起こすのが拡張ではないので、この検出が成立しない。

`source` は取得元を**検出するのではなく、どのコマンドが実行されたかで決める**。クリップボードの中身から出所を推測することはできないため。

## 情報量の段階（contextLevel）

入力経路によって、AIに渡せる情報量が変わる。

| 段階 | 条件                        | 渡せるもの                                 |
| ---- | --------------------------- | ------------------------------------------ |
| Lv3  | VS Code内 かつ 言語拡張あり | 選択範囲 ＋ 前後のコード ＋ 定義や型の情報 |
| Lv2  | VS Code内                   | 選択範囲 ＋ 前後のコード ＋ ファイル・言語 |
| Lv1  | それ以外                    | 選択範囲のテキストのみ                     |

クリップボード経路は Lv1 にあたる。Lv1 はコードに限らず、エラー文、英文、IT用語など任意のテキストを受け付けられる。

## 将来の選択肢

### A. ブラウザ拡張 ＋ localhost 連携

ブラウザ拡張が `window.getSelection()` で選択範囲を直接読み、localhost 経由で VS Code 拡張へ渡す。AI呼び出しは VS Code 側に残す。

- **利点**: ブラウザではコピーが不要になる。`vscode.lm`（ユーザー自身の Copilot を使う）を維持できるのでコスト構造が変わらない
- **検討が必要**: localhost にサーバーを立てると**任意のWebサイトから `fetch` できてしまう**。127.0.0.1 への限定、共有トークンによる認証、`Origin` 検証が必須
- **残る制約**: 対象がブラウザに限られる。VS Code の起動も必要

### B. ネイティブ常駐アプリ

グローバルホットキーを登録し、フォアグラウンドのアプリにコピーを送って選択範囲を取得する。目指す形そのもの。

- **利点**: アプリを問わない。VS Code の起動が不要になる
- **検討が必要**:
  - OSごとに実装が分かれる（macOS はアクセシビリティ権限、Linux の Wayland では合成キー入力が原則できない）
  - 合成キー入力はセキュリティソフトに検知されやすい
  - **`vscode.lm` が使えないため、AI利用料を誰が負担するかの問題が再発する**。ここが最大の論点

### 却下した案

**VS Code にフォーカスが戻った時点でクリップボードを自動で読む**（`onDidChangeWindowState`）。手数は1つ減るが、

- 関係のないコピー（ファイルパス、URL）でも通知が出るため、判別できずノイズになる
- ユーザーの操作なしにクリップボードを読むことになり、学習用ツールとして説明しづらい

減る手数に対して代償が大きいため採用しない。

## キーバインドの変更

既定のキーバインドは `apps/vscode-extension/package.json` の `contributes.keybindings` が配る。

**これは既定値であって、固定値ではない。** 利用者は VS Code 標準の「キーボード
ショートカット」設定（`keybindings.json`）からいつでも上書きできる。だから
**拡張独自のキーバインド設定画面は作らない。** 標準の仕組みと二重に持つと、
どちらが効いているのかが利用者にも実装にも分からなくなる。

足りなかったのは変更する手段ではなく、**その設定画面へ辿り着く導線**だった。
コマンドパレットから `Gakushu Sochi: キーボードショートカットを変更する` を選ぶと、
この拡張のコマンドで絞り込んだ状態で標準の設定画面が開く
（`workbench.action.openGlobalKeybindings` に `gakushuSochi.` を渡す）。

導線そのものには既定キーを割り当てない。衝突の種を増やすだけで、利用頻度に見合わない。

### 既定値の衝突について

`Ctrl + Shift + J` が他の拡張や VS Code 本体の既定と衝突するかは、**実機でしか
確認できない**（`docs/testing.md` の「OS別の確認」）。衝突が実際に観測されたら、
既定値を変えるかどうかをそのときに判断する。**観測がないうちは既定値を動かさない。**
上書きの手段は利用者の側に既にあり、導線もこれで繋がったため。
