# 認証設計（Issue #68 認証周りの統合タスク）

`docs/architecture.md` の「本番化前に明確化する事項」の筆頭にある
**「認証方式と、VS Code の端末ログインフロー」** を確定させ、4つのクライアント
（VS Code Extension / Desktop / Web / API Server）を1つの Identity の上に載せる。

## 1. 先に認めておく制約: 今は誰も認証されていない

**現状のシステムに「利用者」という概念は無い。**

- `apps/api/src/auth/middleware.ts` の `devAuth` は単一の共有トークン
  `DEV_AUTH_TOKEN` を検証し、誰が来ても `DEV_AUTH_USER_ID`（既定 `dev-user`）を返す。
  （§7 のとおり Auth/06 で削除済み。以下は着手時点の記述である。）
- `apps/web/src/worker/index.ts` は `WEB_ACCESS_PASSPHRASE` を知っている全員に
  セッションを配り、`/api/*` の中継時に**共有の** `API_TOKEN` を注入する。
- `apps/vscode-extension` は `gakushuSochi.api.token` 設定に人が手で貼った
  共有トークンを送る。
- `apps/desktop` は同じ共有トークンを OS キーチェーンへ保存する。

つまり `docs/web-viewer.md` が既に認めている通り、

> **ログインは「部外者を入れないゲート」であって、「誰であるかの識別」ではない。**

この状態が引き起こしている結果を、機能の欠落としてではなく**現在の欠陥**として先に書く。

| 現象                                        | 原因                                                       | 影響する Issue |
| ------------------------------------------- | ---------------------------------------------------------- | -------------- |
| 全員の学習イベントが `dev-user` 1行に混ざる | userId がトークンから決まらない                            | #67, #53, #42  |
| レート制限が事実上グローバル                | `rateLimit()` は `userId` で数えるが、その値が全員同じ定数 | #64            |
| AI の利用量・課金を人に紐付けられない       | 同上。`routes/ai.ts` は誰の消費か分からない                | #64, #55       |
| 資格情報を1つ失うと全員分が漏れる           | 個人ごとではなくシステム全体の資格情報                     | —              |

**#64（回数・トークン量の制限）は、Identity が入るまで実装しても機能しない。**
これは依存関係ではなく、着手順に関する結論である。先に本設計を通す。

## 2. 方式の決定

### 2.1 決定: 外部 IdP に委譲する（自前でパスワードを持たない）

自前実装は、パスワードハッシュ・メール確認・リセット・MFA・漏洩対応まで
永続的に抱えることになる。学習ドメインが本体であるこのプロダクトで負う理由が無い。

### 2.2 選定を絞る唯一の制約: Device Authorization Grant

`docs/architecture.md:156` は VS Code に **OAuth Device Authorization Flow** を課している。
理由は実在する。VS Code は Remote-SSH・devcontainer・vscode.dev で動き、
そこでは loopback リダイレクト（`http://127.0.0.1:<port>`）が拡張機能のプロセスと
ブラウザで別ホストになり成立しない。

したがって IdP 候補は **「Device Authorization Grant を公開しているか」で先に篩う**。
各社の一次ドキュメントで確認した結果、**Auth0 に決定した**。経緯を以下に残す。

| IdP    | Device Flow | 確認した制約                                                                                                                                                                                  |
| ------ | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Auth0  | **あり**    | Native アプリ + Device Code グラント有効化 + API(audience) 登録。`Allow Offline Access` で Refresh Token。撤回で端末の再認可を強制できる                                                      |
| GitHub | **あり**    | アプリ設定で**明示的に有効化**が必要。Refresh Token は expiring token 設定時か `offline_access` 要求時のみ                                                                                    |
| Clerk  | **無い**    | 公開している `grant_types_supported` は `["authorization_code", "refresh_token"]` のみ。RFC 8628 のエンドポイントを持たない。Clerk 自身の CLI 認証ガイドも device flow を「対象外」としている |
| Google | 実質不可    | 「TVs and Limited Input devices」種別が必須で、**スコープが `openid`/`email`/`profile` 等に限定**される。自前 API の audience 向けアクセストークンを取れない                                  |

**Clerk はこの1点だけで落ちる。** DX とブラウザ体験は最良だが、VS Code が要求する
grant を提供していない。Clerk を選ぶなら `architecture.md:156` の Device Flow 方針を
捨てるか、VS Code だけ別系統の認証を持つことになる。**4クライアントを1つの Identity に
載せるという本設計の目的そのものと衝突する**ため、採らない。

Google は「TVs and Limited Input devices」のスコープ制限により、自前 API の audience 向け
アクセストークンを取れない。用途と噛み合わない。

残るのは **Auth0** と **GitHub** の2つである。

| 観点                 | Auth0                                                 | GitHub                                                                                 |
| -------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 利用者の前提         | 誰でも（メール / Google / GitHub を後から追加できる） | **GitHub アカウントが必須**                                                            |
| Refresh Token        | `Allow Offline Access` で常時発行                     | expiring token 設定時か `offline_access` 要求時のみ                                    |
| 自前 API の audience | あり（`aud` を検証できる）                            | **無い。** 発行されるのは GitHub API 用トークンで、自前 API 向けの audience を持たない |
| 費用                 | 25,000 MAU まで無料                                   | 無料                                                                                   |
| 撤回                 | Refresh Token 単位で可能                              | ユーザーがアプリ認可を取り消す形                                                       |

**決定: Auth0。**（#68 上で合意済み）

決め手は audience である。GitHub のトークンは「GitHub API を叩くための資格情報」であり、
自前 API 向けの `aud` を持たない。GitHub を IdP にすると、API 側は受け取ったトークンを
毎リクエスト GitHub へ問い合わせて本人を確認することになり、§4 のローカル検証
（署名 / `iss` / `aud` / `exp` を自前で確かめて終わり）が成立しない。
外部依存とレイテンシがリクエストごとに乗る。

副次的に、学習者に GitHub アカウントを必須にしない点も効く。このプロダクトの対象は
「これから学ぶ人」であり、GitHub 前提は入口を狭める。GitHub ログインが欲しければ
**Auth0 の social connection として足せる**ので、Auth0 を選んでも GitHub ログインは
失われない。逆は成立しない。

### 2.3 撤回可能性は交渉の対象にしない

`docs/web-viewer.md:81` が既に決めている。

> JWT にしない。失効させたいときに撤回できないものを、認証の代わりに使わない。

これを Identity 全体へ広げる。**長命で撤回できないアクセストークンを持つ設計は
検討対象から外す。** 具体的には:

- API が受け取るアクセストークンは**短命**（15分程度）にする。
- 長命な資格情報は **Refresh Token だけ**とし、これは IdP 側で撤回できる。
- Web のセッションは現状どおり KV 上の opaque token（撤回可能）を維持する。

短命アクセストークンの JWT 検証は許容する。撤回の単位を Refresh Token に置き、
アクセストークンの寿命を撤回の最大遅延として受け入れる、という取引である。

### 2.4 着手前に確認すること（無料枠で成立するか）

Auth0 の公開資料からは、以下が Free プランで使えるかを**確定できなかった**。
Device Flow のチュートリアルはプラン要件に触れておらず、料金ページは
grant type とアプリ登録数の上限を記載していない。

- **Device Code グラント**を Free プランのアプリで有効化できるか
- **`Allow Offline Access`**（Refresh Token）を Free プランの API で有効化できるか
- **アプリ3つ + API 1つ**を Free プランで登録できるか
  （VS Code と Desktop は同じ Native 種別だが有効化する grant が異なるため、
  1つに相乗りさせず別アプリにする想定）

無料枠に関する確定情報は「25,000 MAU、テナント1、ログ保持1日、管理者3人まで」までである。
**Auth/01 の最初の作業をこの確認にする。** ここが崩れると本設計の前提（無料で始められる）
だけでなく、Device Flow を軸にした選定そのものが変わりうる。
なお、いずれも一般的な grant 設定であって有料機能として案内されている形跡は無いため、
使える見込みは高いと考えているが、**確認していないことは確認していないと書いておく。**

**追記（Auth/01 で確認済み）**: 3アプリ + API 1つの登録、Device Code グラントの有効化、
`Allow Offline Access` ともに Free プランで動作した（§5 の client_id 一覧）。

## 3. 全体構成

```text
                         ┌──────────────────────────────┐
                         │  Auth0（Identity）           │
                         │  - ユーザー、ログイン、MFA    │
                         │  - Refresh Token の撤回      │
                         │  - JWKS 公開                 │
                         └──────────────────────────────┘
             Device Flow ▲      ▲ PKCE+loopback   ▲ Authorization Code
                         │      │                 │
   ┌─────────────────┐   │  ┌───┴──────────┐  ┌───┴─────────────────┐
   │ VS Code Ext     │───┘  │ Desktop      │  │ Web Worker          │
   │ SecretStorage   │      │ safeStorage  │  │ KV: session→RT      │
   └────────┬────────┘      └──────┬───────┘  └───────┬─────────────┘
            │ Bearer <AT>          │ Bearer <AT>      │ Bearer <AT>（サーバー側で注入）
            └──────────────────────┴──────────────────┘
                                   ▼
                     ┌──────────────────────────────┐
                     │ apps/api （Hono / Workers）  │
                     │ verifyAccessToken → userId   │
                     │ → rateLimit(userId) → routes │
                     └──────────────────────────────┘
```

ブラウザにアクセストークンを渡さない。Web は現状の「Worker がトークンを持ち、
ブラウザには Cookie だけ」という形（`docs/web-viewer.md` の案 A）を維持する。
これにより `CORS_ALLOWED_ORIGINS` は空のままでよい。

## 4. API Server の変更

`apps/api/src/auth/middleware.ts` は冒頭で自ら約束している。

> 現時点の検証方式は開発用の共有トークンである。本番の方式へ差し替えるとき、
> 変更はこのファイルに閉じる。

**この約束を守る。** `AuthenticatedUser` / `AuthVariables` の形とハンドラ
（sync / profile / activity / ai）は変えず、`devAuth` を `requireAuth` に差し替える。
ただし完全な無差分ではない。検証の実体を注入するため、`app.ts` の
`app.use("/v1/*", devAuth)` が `app.use("/v1/*", requireAuth)` になった
（`requireAuth` は `createAuth((env) => resolveVerifier(env))`、middleware.ts）。
**変わったのはこの組み立て1行だけ**である。

```ts
export interface AuthenticatedUser {
  userId: string; // IdP の sub をそのまま使う。可変なメールアドレスを主キーにしない
}
```

検証の実体は他のルートと同じく**注入可能**にする。`createLearningEventsRoute((env) => …)`
と同じ形にすることで、`test:unit` が素の vitest のまま（Worker ランタイム無し）で通る。

```ts
export function createAuth(resolve: (env: CloudflareBindings) => AuthVerifier) { … }
```

**継ぎ目は2つ要る。** 上の `AuthVerifier` を差し替える継ぎ目だけでは、
検証器そのもの（署名・`nbf`・Discovery の検証）をテストできない。偽の検証器には
検証すべき署名が存在しないためである。`AuthVerifier` の実装側も、
**Discovery と JWKS の取得に使う `fetch` を注入可能**にする。
そうすればスタブの JWKS と自前で生成した鍵で本物の JWT を検証でき、
WebCrypto は Node にあるので `test:unit` は素の vitest のまま保てる。

検証で確認する項目（1つでも欠けたら 401、設定が欠けていたら 500）:

- 署名（JWKS を取得。**Workers の Cache API でキャッシュし、`kid` 不一致時のみ再取得する。**
  これは最適化ではなくコスト要件である。§10.4）。
  ただし**再取得を無制限にしない**。未知の `kid` を持つトークンを投げ続けるだけで
  Auth0 への外向き通信を1リクエストずつ増やせる。再取得は single-flight にし、
  解決しなかった `kid` には negative cache とクールダウンを置く
- `iss` が設定した issuer と一致
- `aud` が自 API の audience と一致（**これを省くと、同じ Auth0 テナントの
  別アプリ向けトークンで自 API を呼べる**）
- `exp` / `nbf`

`AUTH_ISSUER` / `AUTH_AUDIENCE` は `wrangler.jsonc` の `vars`（秘密ではない）に置き、
**未設定なら 500 で落とす**。

**JWKS の URL は設定項目にしない。** `AUTH_ISSUER` の
`.well-known/openid-configuration`（OIDC Discovery）から導出する。
設定可能にすると「JWKS の取得先だけ攻撃者のサーバーへ向ける」誤設定が成立し、
任意の鍵で署名したトークンが通る。**守るのではなく、設定できなくして消す。**

ただし導出元である `AUTH_ISSUER` を任意の URL のまま受け取ると、
消したはずの穴が一段上に戻ってくる。次を起動時に確かめ、外れたら 500 で落とす。

- `AUTH_ISSUER` は **https で、許可した Auth0 テナント（またはカスタムドメイン）**であること
- Discovery 文書の `issuer` が `AUTH_ISSUER` と**一致**すること
- Discovery が返す `jwks_uri` も **https かつ同じ許可ホスト**であること
  （Discovery 自体が乗っ取られた場合に、鍵の取得先だけ逃がされるのを防ぐ）
  既存の `devAuth` と `rateLimit` が守っている規律をそのまま適用する。
  「設定が無いから全員通す」は、設定漏れがそのまま認証の無効化になる。

## 5. クライアント別の経路

| クライアント      | フロー                                           | 資格情報の置き場所                                 | 置き換える現状                                                                           |
| ----------------- | ------------------------------------------------ | -------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| VS Code Extension | Device Authorization Grant                       | `SecretStorage`                                    | 設定 `gakushuSochi.api.token`（package.json:69）。設定値は同期・共有されうるので廃止する |
| Desktop           | Authorization Code + PKCE / loopback（RFC 8252） | `safeStorage`（`credentials.ts` の継ぎ目を再利用） | 共有トークンの手貼り。#59                                                                |
| Web               | Authorization Code + PKCE（Worker が交換）       | KV（session → Refresh Token）                      | `WEB_ACCESS_PASSPHRASE` + 共有 `API_TOKEN`                                               |
| API Server        | 検証のみ                                         | —                                                  | `DEV_AUTH_TOKEN`                                                                         |

**Auth/01 で登録した実体**（テナント `gakushu-sochi.jp.auth0.com` / JP リージョン）。
`client_id` は秘密ではない（公開クライアントは配布物に埋め込まれる）ため、ここに残す。

| 用途    | Auth0 種別    | client_id                          | grant                                  | token endpoint auth  |
| ------- | ------------- | ---------------------------------- | -------------------------------------- | -------------------- |
| VS Code | `native`      | `QkzWUVBYTbVYoye8SbHxaKbam6sSj014` | `device_code` + `refresh_token`        | `none`（public）     |
| Desktop | `native`      | `r9zPMIsOS9qezfcLkDQq6HC423e0ui0x` | `authorization_code` + `refresh_token` | `none`（public）     |
| Web     | `regular_web` | `EGkN3vMFwcfzJ9RdMDdlIa14OTbgnwRp` | `authorization_code` + `refresh_token` | `client_secret_post` |

API（audience）は `https://api.gakushu-sochi.dev`。`allow_offline_access: true`、
アクセストークンの寿命は 900 秒（§2.3 の「15分」）、署名は RS256。

**`allow_offline_access: true` は Refresh Token 発行の必要条件であって十分条件ではない。**
テナント側でこれを有効にしたうえで、**クライアント側が各認可要求の `scope` に
`offline_access` を含める**必要がある。片方だけでは Refresh Token は返らない。
3クライアントとも §5.1〜§5.3 で個別に指定している。

**Web だけ confidential client である。** Worker がサーバー側で認可コードを交換するため
（§5.3）、client secret を持てる。VS Code と Desktop は配布物に secret を隠せないので
public client + PKCE / Device Flow にする。Web の secret は `wrangler secret put` で
`AUTH_CLIENT_SECRET` として入れる（Auth/05）。

なお **Auth0 は public client にも `client_secret` を発行する**（VS Code / Desktop にも
値が存在する）。`token_endpoint_auth_method` が `none` なので認証には使われないが、
**この2つの secret は使わない。** 配布物に埋め込めば公開されるものであり、
これに依存した実装をすると public client の前提（§9）が崩れる。

### 5.1 VS Code Extension

1. `POST /oauth/device/code` で `user_code` と `verification_uri` を得る。
   **`scope` に `offline_access` を含める**（含めないと Refresh Token が返らず、
   手順4が成立しない）。`audience` に §5 の API identifier を指定する
2. VS Code の通知に `user_code` を出し、`vscode.env.openExternal` で
   `verification_uri` を開く（**Device Flow はクライアントへ戻るリダイレクトを持たない。
   これが Remote-SSH や devcontainer で成立する理由であり、loopback との決定的な違いである**）
3. `interval` を守って `token` エンドポイントをポーリング。`slow_down` を受けたら間隔を伸ばす
4. Refresh Token を `SecretStorage` へ、アクセストークンはメモリのみ

`learning/sync.ts` の `SyncConfig.apiToken` は「毎回取得する短命トークン」になるため、
`() => Promise<string>` を受ける形へ変える。同ファイルの `isSafeApiBaseUrl` と
`redirect: "error"` はそのまま維持する（トークンを載せる相手を検証する意味は変わらない）。
**同期は例外を投げない**という既存の約束も変えない。認証が切れた場合は
`{ ok: false, reason: "再ログインが必要です" }` を返し、質問フローを止めない。

### 5.2 Desktop

ブラウザは既定ブラウザを外部起動する。**埋め込み webview を使わない**
（RFC 8252 が禁じている。アプリがユーザーの資格情報入力画面を覗ける）。
リダイレクトは `http://127.0.0.1:53682/callback`（固定）。
**ポートを固定するのは Auth0 の Allowed Callback URLs がポートにワイルドカードを
使えないため。** ランダムポートにすると起動ごとに redirect_uri が変わり、
何を登録しても `Callback URL mismatch` で弾かれる。ポートを変えるときは
Auth0 の Application 設定（Gakushu Sochi (Desktop)）の登録も同時に変えること。
待受ポートが使用中のときは別ポートへ逃げず失敗させる（逃げた先は未登録で、どのみち弾かれる）。
`state` を検証し、PKCE の `code_verifier` はメモリに持つ。
**認可要求の `scope` に `offline_access` を含める**（含めないと Refresh Token が返らず、
次行の保存対象が存在しなくなる）。`audience` に §5 の API identifier を指定する。
Refresh Token は既存の `createCredentialStore` にそのまま載る。
`crypto.isAvailable()` が false のとき例外を投げる現在の挙動を維持する
（安全に保存できないなら、保存しないのではなく失敗させる）。

### 5.3 Web

`app.all("/api/*")` が共有 `API_TOKEN` を注入している箇所を、
**セッションに紐づくユーザーのアクセストークン**の注入へ変える。

- **認可要求の `scope` に `offline_access` を含める。** `/login` から IdP へ飛ばすときに
  含めないと Refresh Token が返らず、KV に保存する対象（下記）が存在しなくなる。
  `audience` には §5 の API identifier を指定する
- **`state` を検証する。** `/login` で乱数の `state` を作り、短命の pre-session Cookie に
  紐付けて保存する。`/callback` では受け取った `state` と保存値が一致することを
  **Refresh Token を保存する前に**確かめ、違えば中断する。
  PKCE は認可コードの横取りを防ぐが、**ログイン CSRF は防がない**
  （攻撃者が自分の認可コードを踏ませ、被害者を攻撃者のアカウントでログインさせる）。
  §5.2 の Desktop には既に `state` があり、Web だけ無いのは漏れである
- KV の値を `"1"` から `{ refreshToken, sub }` へ広げる（`session.ts`）
- 中継の直前にアクセストークンを取得する。**AT は KV へ書かない**
  （KV 書き込みは読み取りの10倍の単価で、AT の寿命15分だとセッションあたり
  最大4回/時の書き込みになる。§10.4）。Worker のメモリにキャッシュし、
  KV に置くのは Refresh Token だけにする
- **Refresh の失敗を一律に扱わない。** セッションを消して 401 `session_expired` を返すのは
  `invalid_grant`（RT が失効・撤回済み）のときだけにする。
  タイムアウト・5xx・レート制限・ネットワーク障害では**セッションを残し**、
  再試行可能なエラーを返す。ここを区別しないと、**Auth0 側の一時的な 5xx 一回で
  全利用者がログアウトさせられる**
- **Refresh Token Rotation の同時実行を直列化する。** Auth0 は Native / SPA で
  rotation が既定であり、回すたびに古い RT が無効になる。1セッションに複数リクエストが
  同時に来ると両方が同時に refresh し、片方が取得した新しい RT をもう片方が
  古い値で上書きして、利用者がランダムにログアウトする。
  セッション単位で single-flight にし、KV へ書き戻すときに**新しい方を消さない**。
  実装手段（Durable Object を使うか、KV の楽観的更新で足りるか）は Auth/05 で決める。

  **Auth/01 で固定した値（3アプリ共通）**:

  | 項目                       | 値                   | 理由                                                                  |
  | -------------------------- | -------------------- | --------------------------------------------------------------------- |
  | `rotation_type`            | `rotating`           | 撤回可能性を保つ（§2.3）。回すたびに古い RT が無効になる              |
  | `expiration_type`          | `expiring`           | rotation に必須。既定の `non-expiring` だと下の有効期間が無視される   |
  | `leeway`（reuse interval） | **30 秒**            | 0 だと再送1回で RT ファミリ全体が失効し、利用者が強制ログアウトになる |
  | `token_lifetime`（絶対）   | 2,592,000 秒（30日） | 30日触らなければ再ログイン                                            |
  | `idle_token_lifetime`      | 1,209,600 秒（14日） | VS Code は週数回の利用を想定。短すぎると再認可が頻発する              |

  **rotation を選んだので、上記の single-flight は必須である。**
  `leeway` 30 秒は競合を緩和するが、解消はしない。並行 refresh が leeway を
  超えてずれた場合は依然として RT ファミリが失効するため、直列化を省略できない。

  **決定（Auth/05）: Durable Object ではなく、Worker isolate 内のメモリで直列化する。**

  まず **KV の楽観的更新は選択肢として成立しない**。Workers KV に条件付き書き込み
  （CAS）が無いためである。`put` は無条件の上書きしか持たず、読んだ値に基づいて
  「変わっていなければ書く」を表現できない。残るのは DO かメモリの二択になる。

  メモリを採る理由は次の 3 つ。

  1. この競合が起きるのは**1 人のブラウザが同時に投げる数本の要求**である
     （画面は `Promise.all` で習熟度と手動上書きを並べて取る）。
     同時に飛ぶ数本は同じ isolate へ入るのが通常で、メモリの single-flight が効く。
  2. isolate をまたいで残る競合は `leeway` 30 秒が吸収する。
     leeway は競合を**解消しない**が、この幅の同時実行は救う。
  3. DO を 1 つ入れると、この Worker に永続オブジェクトの運用とデプロイ手順が付く。
     利用者がまだ居ない段階で、効果の差が「leeway を超えるずれ」だけの機構を先に抱えない。

  **この決定が破れる条件を先に書いておく。** 次のどちらかが実害として観測されたら
  DO へ移す。そのとき変わるのは `apps/web/src/worker/access-token.ts` の中だけで、
  呼び出し側（`index.ts`）の形は変えずに済むようにしてある。

  1. isolate をまたぐ並行 refresh が leeway 30 秒を超えてずれ、
     利用者がランダムにログアウトする
  2. ログアウトと並行する refresh が、消したセッションを KV へ蘇らせる

  2 について、同一 isolate 内は失効マーカーで塞いである（`await` のたびに確認し、
  KV へ書いた後に失効が判明したら自分で消す）。ただし**これは順序の同期ではなく
  事後の打ち消し**であり、別 isolate の refresh には届かない。
  露出はログアウト時の `/oauth/revoke` と AT の寿命 15 分で上限される（§9）。

これに伴う波及:

- **`wrangler.jsonc` の `run_worker_first` に `/callback` を追加する。**
  忘れると assets バインディングが `index.html` を返し、
  **認可コードの交換が Worker に届かないまま静かに失敗する**。
  `docs/web-viewer.md:99` が既に警告している罠であり、経路を増やすたびに踏み直す。
  `/login` は IdP へのリダイレクト開始点として残るので、配列から外さない。
- `wrangler.jsonc` から secret `API_TOKEN` と `WEB_ACCESS_PASSPHRASE` が消える
- `apps/web/src/client/api.ts` の `ApiErrorKind` から `api_token_invalid` が消える
  （共有トークンが無くなるので、この状態自体が存在しなくなる）。
  代わりに `auth_unavailable` が入る。**これは「セッションは生きているが IdP が
  一時的に応答しない」状態**で、上の「refresh の失敗を一律に扱わない」を
  画面まで通すために要る。利用者への指示が「再ログイン」ではなく「再試行」になる
- `LOGIN_RATE_LIMITER`（IP 単位）は**残す。用途を変える**。
  パスワード試行の制限は IdP の責務へ移るが、`/login` と `/callback` は認証前の
  エンドポイントであり、叩かれれば Auth0 への外向き通信が発生する。
  数える対象を「ログイン試行」から「認証前エンドポイントへの到達」へ読み替えて維持する。
  認証済みユーザーが居ない経路なので、鍵は引き続き `CF-Connecting-IP` になる

## 6. 既存データの扱い（決めておかないと後で直せなくなる）

`learning_events` と `devices` の既存行は**全て `user_id = 'dev-user'`** である。
主キーは `(user_id, id)` で、イベント ID はクライアント生成。

**決定: `dev-user` の行は移行せず破棄する。**

理由は、そのデータが誰のものか**判定する材料がサーバーに無い**ため。
`client_id` は端末の自己申告であり、認証済みの identity ではない。
「最初にログインした人が引き取る」方式は、実際には複数人の混ざったログを
1人のものとして確定させ、その人の Learning Map を恒久的に汚す。
学習イベントは追記のみで後から書き換えないという前提（`migrations/0001_initial.sql`）とも
噛み合わない。

移行スクリプトではなく、カットオーバー時に `DELETE FROM users WHERE id = 'dev-user'`
を実行する（両子テーブルが `ON DELETE CASCADE` なので1文で足りる）。
**この判断は確認済みで確定している**（#68 上で「dev-user は消えても大丈夫」と合意）。

## 7. 古い扉を閉じる

**この節は Auth/06（#85）で完了した。** 以下は決定と、実際に踏んだ手順の記録である。

`DEV_AUTH_TOKEN` と `WEB_ACCESS_PASSPHRASE` は、どちらも**全権限のバイパス**であった。
新しい認証と並存させたまま残すと、恒久的な裏口になる。
「動いているから消し忘れる」が最も起こりやすい失敗なので、独立したタスクにした。

カットオーバー手順:

1. `requireAuth` を実装し、`AUTH_*` を設定する（この時点では未接続）— Auth/02
2. 全クライアントが新フローで疎通することを確認する — Auth/03〜05
3. `devAuth` を削除し、`DEV_AUTH_TOKEN` / `DEV_AUTH_USER_ID` を
   `wrangler.jsonc` と `wrangler secret delete` の両方から消す — Auth/06
4. Web から `WEB_ACCESS_PASSPHRASE` / `API_TOKEN` を同様に消す — Auth/05 で実施済み

   ただし**消えていたのはコードと設定だけで、secret は生きていた。** Auth/06 で
   Cloudflare の `API_TOKEN` / `WEB_ACCESS_PASSPHRASE` と、GitHub Actions の
   `WEB_ACCESS_PASSPHRASE` / `WEB_API_TOKEN`（production environment）を削除した。
   **設定から参照が消えても、secret が残っていれば裏口は開いたままである。**
   消す場所は「コード・設定・Cloudflare・GitHub」の4つあると数えること。
   再発防止として `test/package-scripts.test.mjs` が、これらの名前が
   workflow に現れたら落ちるようにしてある。

5. `dev-user` を削除する（第6節）— Auth/07（#86、未完）

テストが `devAuth` を「userId を決めるだけの都合のよいミドルウェア」として流用していた
ことが、共有トークンを消せない隠れた理由になっていた。`apps/api/src/auth/test-auth.ts` の
`stubAuth` へ移し、本番と同じ `createAuth` に偽の検証器を挿す形へ揃えてある。
**テストの都合で資格情報を残さない。**

## 8. 撤回・ログアウト・退会

| 操作                           | 実装                                                                                                                                |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| Web ログアウト                 | KV のセッション削除（現状のまま）+ IdP の Refresh Token 撤回                                                                        |
| Desktop / VS Code のログアウト | ローカルの Refresh Token 破棄 + `POST /oauth/revoke`                                                                                |
| 端末を紛失した                 | IdP 側で当該 Refresh Token を撤回。**最大でアクセストークンの寿命（15分）だけ遅延する**                                             |
| 退会                           | `DELETE FROM users WHERE id = ?` の1文で learning_events / devices が消える（`ON DELETE CASCADE` 済み）。IdP 側のユーザーも削除する |

**順序を決めておく。退会は D1 を先に消し、その後 Auth0 のユーザーを消す。**
逆にすると、Auth0 のユーザーが消えた後に D1 の削除が失敗した場合、
**二度と認証できない `sub` の下に学習データだけが残る**（保持期間の問題になる）。
この順序なら、Auth0 側の削除に失敗しても利用者は空のアカウントにログインし直せるだけで、
再実行すれば済む。

ログアウトも同様に、**先にローカルの Refresh Token を破棄する**。
利用者を守っているのはローカルの破棄であり、`POST /oauth/revoke` の成否ではない。
撤回に失敗した場合は**握りつぶさずログへ残す**（AGENTS.md）。
露出はアクセストークンの寿命に上限される。

なお、定期的な突合ジョブや撤回の永続リトライキューは**今は作らない**。
利用者がまだ居ない段階で運用機構を先に作ると、必要な形が分からないまま固定される。
失敗が観測できていれば、手で直せる。

退会が安いのはスキーマが既にそう作られているからで、後回しにする理由が無い。
`docs/architecture.md`「本番化前に明確化する事項」の「退会後の扱い」はここで閉じる。

## 9. 認めておくこと

- **アクセストークンの寿命が撤回の遅延になる。** 15分は即時ではない。
  即時撤回が要るなら API 側で denylist を持つことになる。
  これを採らない理由は**コストではない**（KV 読み取りは Free で 10万回/日、
  Paid なら月1000万回まで込み。本プロダクトの規模では毎リクエスト読んでも実質0円である）。理由は、撤回の正本が
  IdP と denylist の2箇所に分かれ、片方だけ書けた状態が「撤回したつもりで生きている
  トークン」になるためである。要件が変わったら見直す。
- **Refresh Token はローカルに残る。** OS キーチェーン / SecretStorage が守るのは
  「他のアプリから読めない」までであり、端末を掌握した攻撃者からは守れない。
  だからこそ撤回できることを条件にしている。
- **`packages/domain` は認証を一切知らない。** userId は文字列として渡るだけである。
  この境界は Identity を入れても動かさない。
- **Auth0 の無料枠に依存する。** テナントを失うと全員がログインできない。
  userId に IdP の `sub` を使うため、IdP 移行時はユーザーの再紐付けが必要になる。
  移行が視野に入ったら、`users` に IdP identity を別テーブルで持つ形へ広げる。

## 10. 運用コスト

**結論を先に書く。認証方式の選択で動く金額は小さい。動くのは AI の請求であり、
認証はその上限を持てるようにするための前提である。**

### 10.1 本当の危険は AI Gateway にある

**この節は着手時点（Auth/10 の実装前）の記述である。** 上限は実装済みで、
現在の `routes/ai.ts` は下記の試算どおりには動かない（本節の末尾「実装後の状態」を参照）。
記録として残すのは、**上限を外したときに何が起きるか**がここにしか書かれていないためである。

`routes/ai.ts` は `selection` 20,000字 + `question` 4,000字 を受け付け、
`maxTokens` は 16,384 まで指定できる。適用されるのは `PROFILE_RATE_LIMITER`
（30回/分 = 43,200回/日）である。

Gemini Flash の料金（入力 $0.75 / 出力 $3.75 per 1M tokens、2026年12月31日まで。
2027年1月1日から倍額）で、上限いっぱいのリクエストを試算する。
**この試算は設定された Flash モデルを使う前提である。**
実際には `routes/ai.ts:9` がリクエストの `model` を任意の文字列で受け付けており
（allowlist が無い）、クライアントは単価の高いモデルを名指しできる。
Gemini 3.5 Flash の単価（入力 $1.50 / 出力 $9.00）なら同じ上限で約2.4倍になる。
**モデルの allowlist 化を Auth/10 に含める。**

| 項目                   | 値                                                    |
| ---------------------- | ----------------------------------------------------- |
| 1リクエスト最大        | 入力 約12,000 tokens + 出力 16,384 tokens ≒ **$0.07** |
| 1「ユーザー」1日の上限 | 43,200回 × $0.07 ≒ **$3,000**                         |
| 同 1ヶ月               | **約$91,000**                                         |

**そして現在、この「1ユーザー」は `dev-user` ただ1人である。**
`DEV_AUTH_TOKEN` の文字列を持っている者なら誰でもこの枠を消費でき、
しかも**誰が使ったのか特定できず、その1人だけを止めることもできない**。
共有トークンが1つ漏れた時に取れる手は、全員のサービスを止めることだけになる。

**上限値そのものは決定済みである。** Free / Pro の区分と、Managed AI の
日次・月次のトークン上限、上限到達時の挙動は
[`docs/ai-limits.md`](ai-limits.md)が正典である
（**当面 Free のみ。1人あたり月 150 回 / 日 15 回、かつ1回あたり入力 6,000 + 出力 2,048 tokens。
上限到達時は Managed AI だけを 429 で止め、Copilot / BYOK へ案内する**）。
**月150回は仮置きで、利用実績が取れたら見直す前提の数字である。**
この節は「上限が無いと何が起きるか」を示す側であり、**数字を変えるときは
`ai-limits.md` を直す。** Auth/10 が実装する上限値はそこから読む。

これが「認証方式の違いによるお金の心配」への答えである。
心配すべきは IdP の料金ではなく、**個人を識別できないと支出に上限を掛けられないこと**。
Auth/10（AI 利用量の計測と上限）はやり残しの改善ではなく、**コスト管理の本体**である。

#### 実装後の状態（Auth/10 / #89）

上の試算を成り立たせていた3つの穴は塞いである。

| 穴                             | 塞ぎ方                                                                                                                              | 実装                                       |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `model` が任意の文字列         | allowlist。許可外は 400 で拒否し、上流を呼ばない                                                                                    | `contract/ai-usage.ts` の `ALLOWED_MODELS` |
| 1回あたりの上限が無い          | 入力 6,000 / 出力 2,048 tokens。入力超過は**切り捨てず 400**、`maxTokens` はスキーマで弾く。入力の判定は UTF-8 バイト数で上界を取る | `routes/ai.ts`                             |
| トークンを数えている場所が無い | 素通しをやめ、SSE を**本文を書き換えずに**通しながら `usageMetadata.totalTokenCount` を拾って D1 へ蓄積する                         | `routes/ai.ts` の `meterUsage`             |

回数は**上流へ流す前**に数える。完了を待ってから数えると、応答を読み切らずに
切断する呼び出しを繰り返すだけで上限を素通りできる。

さらに**判定と加算は1つの操作にまとめる**（`AiUsageRepository.reserve`）。
読んでから別の文で足すと、同じ利用者の同時リクエストがその隙間に割り込み、
**上限を超えて弾いた分まで枠を消費する**。15回の枠へ30回同時に来たとき、
通るのは15回なのに月次からは30回引かれる、という取りこぼしになる。
D1 では `ON CONFLICT ... DO UPDATE ... WHERE` で条件付きに加算する。

両方の上限に達している利用者には、**遠いほうの回復時刻**を返す。
日次の「明日 UTC 0時」を返すと、その時刻に再試行しても月次で止まり続ける。

蓄積先は **D1 を選んだ**（`migrations/0004_ai_usage.sql` に理由を書いてある）。
退会が `DELETE FROM users` 1文で全データを消せるという前提を崩さないこと、
1ユーザー月150回という頻度が KV の書き込み単価（読み取りの10倍。§10.4）に
見合わないことの2点による。

#### 現在は Gemini の無料枠である（2026-09-09 時点。将来的に有料枠へ移行予定）

**2026-09-09 時点の AI 請求は $0** であり、上の試算は有料枠へ移った後に効いてくる数字である。
ただし「無料枠かどうか」は請求額が $0 であることでは確定しない。
Gemini API の課金区分は **Cloud プロジェクトに課金アカウントが紐付いているか**で決まるため、
プロジェクト側の設定を確認して記録すること。確認できるまでは、
下記のデータ利用条件が適用される前提（=機密情報を送らない）で扱う。
ただし無料枠には金額以外の代償があり、それは請求書に現れない。

Gemini API の利用規約では、**無料枠は Google が送信内容と生成結果を自社プロダクトの
改善・機械学習に利用し、人間のレビュアーが読む可能性がある**
（レビュー前にアカウントと API キーからは切り離される）。
有料枠では「プロンプトや応答をプロダクト改善に利用しない」と明示されている。

`docs/data-privacy.md` は、選択範囲・質問本文・診断メッセージに
**業務上の機密情報や個人情報が含まれうる**と認めている。
`routes/ai.ts` が Google へ送っているのは、まさにその `selection` と `question` である。

**つまり無料枠のままの運用は、コストの問題ではなくデータ方針の問題である。**
有料枠への移行は「請求が発生する変更」であると同時に「送信内容が学習に使われなくなる
変更」でもあり、後者のほうが重い。移行時期はこの順序で評価する。
それまでの間は、送信内容の扱いを利用者へ明示する責任がある
（`docs/data-privacy.md`「同意を取るまで送らない」）。

**有料枠へ移る前に Auth/10（利用量の計測と上限）を先に入れること。**
無料枠はレート制限が事実上の防波堤になっているが、有料枠にすればその壁が外れ、
§10.1 の試算がそのまま請求額になりうる。順序を逆にしない。

無料枠を超える現実性はこのプロダクトには無い（超えているなら別の心配をしている）。
ただし**跳ね方は緩やかではない**ことは認識しておく。Auth0 は「$35から」と読めるが、
それは 500 MAU の値段であって、無料枠を抜けた瞬間の値段ではない。

### 10.3 MAU の数え方（保守的に見積もる）

背景トークン更新を持つクライアント（VS Code / Desktop）では、
**「誰も操作していないのに課金対象になり続けるのか」**が効いてくる。
Auth0 の MAU 算入イベント一覧には
`sertft`（Successful exchange of Refresh Token for Access Token）が**含まれている**。

つまり同期がバックグラウンドで走るだけで、その月の MAU に数えられる。
MAU は「今月学習した人」ではなく「今月アプリが起動した人」に近い。
無料枠内では影響しないが、課金の見積もりを立てるときにこの定義を使うこと。
