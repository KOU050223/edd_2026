# Free / Pro の境界と Managed AI の利用上限

この文書が Free / Pro の区分の正本である。上限の**実装**は #89（Auth/10）が持ち、
この文書は**その実装が埋めるべき数字**を決める。数字を変えるときはここを直す。

**実装済み（#89）。** この文書の数字は `apps/api/src/contract/ai-usage.ts` の
`AI_USAGE_LIMITS` へ写してあり、値が一致することを
`apps/api/src/contract/ai-usage.test.ts` が固定している。
**ここを直したらそのテストが落ちる。** 落ちたテストを直すのが実装への反映である
（先にコード側だけを変えると、正本とのずれが誰にも見えないまま残る）。

## 決定: 当面 Free のみ。Pro は作らない

課金区分を1つにする。**Pro は作らず、全員が同じ Free の上限で使う。**

利用者が実際に増え、上限に当たる人が続けて現れたときに初めて Pro を設計する。
その時点まで決済を導入しない。決済は返金・請求・失効の運用を連れてくるため、
必要が観測されるまで負債にしかならない。

**「当面 Free のみ」は「上限を決めない」ことではない。** 単価のある経路を
無認証・無上限で開けたままにしないために、Free の上限をこの文書で数字にする。

## 決定: Managed AI は Free に含める

Managed AI（運営が Gemini を叩く経路）を **Free に含める**。上限付きで開放する。

含めない選択もありえた。その場合 Free の利用者は Copilot 契約か BYOK（#55）が前提になり、
**「インストールしたが AI が何も動かない」利用者**が既定になる。
Gakushu Sochi の中心的な価値は Personal Learning Map であり、そこへ到達するには
まず質問が成立していなければならない。最初の質問が通らない状態で学習の軌跡は溜まらない。

代わりに、**上限を低く置いて BYOK と Copilot を「上限の外へ出る道」にする。**
この順序なら #55 は公開の前提条件ではなく、上限に当たった利用者への出口になる。

## 上限値

**回数で数える。** 利用者に見える単位と、課金を止める単位を一致させる。

<!-- ここが政策値である。ビジネス判断で動かすのはこの表だけにする。 -->

| 項目                         | 値               | 種別   |
| ---------------------------- | ---------------- | ------ |
| 月間リクエスト（暦月・UTC）  | **150 回**       | 政策値 |
| 日次リクエスト（UTC）        | **15 回**        | 政策値 |
| 1回の入力上限                | **6,000 tokens** | 政策値 |
| 1回の出力上限（`maxTokens`） | **2,048 tokens** | 政策値 |

**月150回は仮置きである。** 実利用の分布が取れていないため、
予算に収まる範囲で保守的に置いた。緩める前提の数字であり、
根拠は下の「上限額の試算」にある。変更手順は「この数字を後から動かす」を参照。

日次を併記するのは、月次だけだと初日に1ヶ月分を使い切られ残りが使えなくなるためである。
15回 × 31日 = 465回 で月次（150回）が先に効くので、**日次は瞬間的な暴走を止める役**であり、
実質的な上限は月次が持つ。

### 1回あたりの上限が回数上限の前提である

**回数上限は、1回あたりの上限と対でなければ金額を保証しない。**

`apps/api/src/routes/ai.ts` は**着手時**、`selection` 20,000字・`maxTokens` 16,384 を
受け付けていた。この幅のままだと1回の単価が**典型の15.7倍**まで振れ、
「月150回」が $0.68 から $10.57 まで動く。回数を数えても金額が決まらない。
#89 でこの幅を下の「上限」の行まで絞ってある。

| 1回の内容                                   | 単価        | 典型との比 |
| ------------------------------------------- | ----------- | ---------- |
| 典型（入力 2,000 + 出力 800）               | $0.0045     | 1倍        |
| **上限**（入力 6,000 + 出力 2,048）         | **$0.0122** | **2.7倍**  |
| 現在の受付上限（入力 12,000 + 出力 16,384） | $0.0704     | 15.7倍     |

上限を掛けることで振れ幅を **15.7倍 → 2.7倍** に縮める。
この 2.7倍 を最悪ケースとして試算に使う。

**入力の超過は切り捨てず拒否する。** 黙って切ると、利用者から見て
AI が文脈を読み落とした状態になり、原因が分からない
（`.agents/rules/rules.md` RULE-004）。上限を超える入力は
**400 と、超過していることが分かる理由**を返す。

**入力トークンの判定は UTF-8 のバイト数で行う**（#89 のレビュー指摘）。
`String.length` は UTF-16 のコード単位なので、日本語1文字が 1 と数えられる。
しかし tokenizer の byte fallback は未知の文字を**1バイトにつき1トークン**まで
分解しうるため、文字数で見ると実際の3〜4倍を見落とし、1回あたりの単価の上限が崩れる。
バイト数を上界として使うと**常に過大**に見積もることになり、通った入力は必ず上限内に収まる。

その代わり、**利用者から見た分量は言語で変わる。** 6,000 tokens は
日本語で約 1,990 文字、英数字で約 5,970 文字にあたる。拒否の文面にはこの目安を載せる。

### トークンでも数え、どちらか早い方で止める

回数の裏で**トークンの累計も記録する**（月 1,300,000 tokens を上限とする）。
これは利用者へ見せる数字ではなく、**回数上限の想定が崩れたときの安全弁**である。

1回あたりの上限を掛けても、想定が外れることはある
（プロンプトの作り方が変わる、`ProfileSummary` が膨らむ、モデルの
トークン化が想定と違う）。回数だけで止めていると、
1回の実消費が想定を超えた分だけ請求が素通りする。

月150回 × 1回の上限 8,048 tokens = 1,207,200 tokens が理論上の最大である。
安全弁はその約1.08倍に置く。**通常は回数が先に尽きる**ため、
この上限に当たること自体が「想定が外れた」という信号になる。
当たったらログへ残し、政策値を見直す。

### 利用者への見せ方

**残量は回数で示す。** 「残り 23 回 / 150 回」「明日 UTC 0時に 15 回へ回復」。
トークン数は利用者へ見せない。単価の違い（出力は入力の5倍）を意識しなければ
残量を予測できない単位であり、説明の手間に見合わない。

トークンの安全弁に当たった場合も、利用者へは**回数と同じ扱い**で見せる
（上限に達した、いつ回復する）。内部の別勘定を利用者へ説明しない。

| -------------------------------------- | ---------------- | ---------------- | ------------------------------------ |
| `gemini-3.6-flash`（既定・上限の根拠） | **$0.75**        | **$3.75**        | 2026-12-31 まで。2027-01-01 から倍額 |
| `gemini-3.8-flash`                     | $0.75            | $3.75            | 同上。2027-01-01 から $1.50 / $7.50  |
| `gemini-3.5-flash`                     | $1.50            | $9.00            | 既定より高い。allowlist で塞ぐ対象   |
| `gemini-3.5-flash-lite`                | $0.30            | $2.50            | 退避先の候補                         |

既定モデルは `apps/api/src/routes/ai.ts` の `gemini-3.6-flash` に合わせている。

**2027-01-01 に単価が倍になる。** 上限を回数で固定しているため、
同じ上限のまま**上限額だけが2倍になる**（200人で $365 → $731）。下の試算に 2027 年以降の列を併記してあるのは、
その日に何も気づかないまま請求が倍になるのを避けるためである。

## 上限額の試算

**1回あたりの上限（入力 6,000 + 出力 2,048）を最悪ケースとして使う。**
実際の請求は典型ケースとの間に収まる。

| 想定                      | 1回     | 1人あたり月次（150回） | 2027-01-01 以降 |
| ------------------------- | ------- | ---------------------- | --------------- |
| 典型（入力2,000+出力800） | $0.0045 | $0.68                  | $1.35           |
| **上限いっぱい（最悪）**  | $0.0122 | **$1.83**              | $3.65           |

利用者数を掛けた運営側の月次上限は次のとおり。**上限が効いていれば**この額を超えない。

| 想定利用者数 | 月次の最大（最悪ケース） | 2027-01-01 以降 | 典型ケース |
| ------------ | ------------------------ | --------------- | ---------- |
| 50人         | $91                      | $183            | $34        |
| 200人        | **$365**                 | $731            | $135       |
| 1,000人      | $1,827                   | $3,654          | $675       |

**200人で月$365 を許容できる上限として採った**（予算 $375 以内）。
個人が運営する学習プロダクトとして、不正利用が最大まで起きても
月額が3桁ドルで止まることを条件にしている。
1,000人規模へ伸びた時点では、この文書と Pro の有無を再検討する。

比較のため、`docs/auth.md` §10.1 の**上限を入れる前**の試算は
**1ユーザーの日次 約$3,000 / 月 約$91,000** である。
回数の制限（30回/分）だけではトークン量に上限が無く、1リクエストが最大 $0.07 に達するためである。
この文書の上限は、その1人月を **$91,000 → $1.83** にする。

## この数字を後から動かす

**上限値はビジネス判断で動く前提で置いている。** 動かすときの手順を固定しておく。

### 動かしてよいもの / 動かすと設計が変わるもの

| 対象                      | 変更の重さ                                                        |
| ------------------------- | ----------------------------------------------------------------- |
| 月間・日次の回数          | **軽い。** 「上限値」の表と下の換算表を直すだけ                   |
| 1回あたりの入力・出力上限 | **中。** 回数の意味が変わるので試算をやり直す                     |
| 許容する月額（予算）      | **中。** 上の試算から回数を引き直す                               |
| 回数で数えること自体      | **重い。** 利用者への見せ方と #89 の実装方針が変わる              |
| Free / Pro の区分         | **重い。** 決済の運用が増える。この文書の「当面 Free のみ」を覆す |

### 予算から回数を引き直す

許容月額を変えたら、次の式で回数を出す。

```text
1人あたり月の許容額 = 許容月額 ÷ 想定利用者数
月間回数            = 1人あたり月の許容額 ÷ 1回あたりの最悪単価
1回あたりの最悪単価  = 入力上限 × 入力単価 + 出力上限 × 出力単価
```

現在の値で検算すると
`$375 ÷ 200人 = $1.88/人月`、`$1.88 ÷ $0.0122 = 約154回` → **150回**（切り下げ）。

参考として、1回あたりの上限を据え置いたまま回数だけ動かした場合の 200人での最悪月額:

| 月間回数      | 200人での最悪月額 | 判定               |
| ------------- | ----------------- | ------------------ |
| 150回（現行） | $365              | 予算内             |
| 300回         | $731              | 予算 $375 を超える |
| 500回         | $1,218            | 予算の3.2倍        |

**「月500回」を予算 $375 のまま名乗ることはできない。** 名乗るには
1回あたりを合計 2,273 tokens（出力だけなら1,000 tokens）まで絞る必要があり、
解説が途中で切れる長さになる。これは上限ではなく機能の劣化である。
回数を増やすなら、**予算を上げるか、利用者数の想定を下げるかを先に決める。**

### 変更時に必ず一緒に直す場所

数字を動かしたら、次を同じ変更で直す。**片方だけ直すと食い違う。**

1. **この文書の「上限値」の表**（政策値の正本）
2. **「上限額の試算」の表**（金額の根拠）
3. **トークンの安全弁**（月間回数 × 1回の上限 の約1.08倍に置く）
4. **#89 の実装値**（上限はコードに定数で持たせ、この文書の値を出典としてコメントに書く）
5. **利用者へ見せている残量表示**（「N 回 / 150 回」の分母）

**上限値をコードに散らさない。** #89 では1箇所の定数へ集約し、
この文書へのリンクをコメントに置く。上限は実装の詳細ではなく政策であり、
変更のたびに探し回る状態にしない。

## 上限に達した後の挙動

**Managed AI だけを止める。学習の記録と閲覧は止めない。**

1. **Managed AI の要求を拒否する。** `POST /v1/ai/responses` は
   **HTTP 429** と、上限到達であることが判別できる機械可読な理由、
   および**上限が回復する時刻**（日次なら翌 UTC 0時、月次なら翌月1日）を返す。
   回数のレート制限（30回/分）とは別の理由コードにする。
   利用者が「1分待てば直るのか、月が変わるまで駄目なのか」を区別できなければ、
   どちらも「よく分からないが失敗した」になる。
2. **上限に達する前から残量を返す。** 成功応答にも残量（残り回数と上限）を含める。
   上限に当たって初めて存在を知る上限は、利用者にとって突然の停止と区別できない。
3. **学習イベントの同期と Learning Map の閲覧は通常どおり動かす。**
   上限はコストのある経路だけに掛かる。
   `learning-events:sync` と `learning-profile` に上限を適用しない。
4. **Copilot と BYOK へ案内して継続させる。** 停止ではなく経路の切り替えを促す。
   この2つは利用者の契約と鍵で動くため、運営のコストに掛からず上限の対象外である。
   案内はクライアント側で出す。VS Code は Copilot（`vscode.lm`）へ、
   Copilot 未契約なら BYOK（#55）へ誘導する。

**上限を超えたぶんを黙って縮めない。** `maxTokens` を勝手に小さくして応答を
短く切る、より安いモデルへ黙って落とす、といった処理をしない。
利用者から見て「AI が急に頭が悪くなった」という説明のつかない状態になるためである
（`.agents/rules/rules.md` RULE-004「フォールバックで失敗を隠さない」）。
安いモデルへの退避を選ぶなら、**選んだことが利用者に見える形で**行う。

## 併せて必要なこと

- **モデルの allowlist 化。** 現在 `apps/api/src/routes/ai.ts` は `model` を
  任意の文字列で受け付ける。回数と1回あたりを固定しても、単価の高いモデルを
  名指しされれば上限額は跳ねる（`gemini-3.5-flash` で約2.4倍）。
  **上限値と allowlist は両方揃って初めて上限額を保証する。** #89 に含める。
- **上限は Gemini を有料枠へ移す前に入れる。** 無料枠ではレート制限が
  事実上の防波堤になっているが、有料枠にするとその壁が外れる（`docs/auth.md` §10.1）。

## 前提と、確認できていないこと

- **Gemini 無料枠の日次リクエスト上限（RPD）をモデル別に確認できなかった。**
  料金ページとレート制限ページは 2026-09-21 時点でモデル別の RPD を公開しておらず、
  「AI Studio のダッシュボードで確認せよ」としている。
  **上限値は有料枠の単価から逆算しており、無料枠の枠内に収まるかは未確認である。**
  無料枠のまま運用する間は、Google 側の上限に先に当たる可能性がある。
  実測して分かった時点でここへ書く。
- **上記の「典型的な質問」の規模（入力 2,000 / 出力 800 tokens）は想定値である。**
  Managed AI は未実装のため実績が無い。#89 で計測が入ったら実測値へ置き換え、
  上限値が実際の使用感と合っているかを見直す。
- **月150回そのものが仮置きである。** 実利用の分布が無い状態で、
  予算 $375 から逆算した上限（154回）を切り下げただけの数字である。
  **利用実績が取れたら見直す前提で置いている。** 見直しの手順は
  「この数字を後から動かす」にある。1回あたりの上限（入力 6,000 / 出力 2,048）も同様で、
  実際の質問がこれに収まるかは #89 の計測で確認する。
- **想定利用者数 200人も想定値である。** 現時点の利用者は `dev-user` 1人である。
