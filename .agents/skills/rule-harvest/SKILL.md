# ルール候補の棚卸し

`npm run harvest:rules` が出したルール候補を、**採用か却下のどちらかに倒しきる**ための手順。
放置した候補は次の `main` への push でまた Issue になる。

## 原則 — ここを踏み外さない

**採否を決めるのは人間である。** このスキルがやるのは、候補の取得・分類・下書きの作成・
書式の検証までで、そこで**必ず止まって提案を出す**。
`docs/guardrails.md` が「ルールの追記は自動化しない」と明記しており、
勝手に `rules.md` へ書き込むとリポジトリが自分の設計方針と矛盾する。

理由もそこに書いてある。エージェントがルールを書き足せるようにすると、
ルール集はすぐに「誰も読まない長さ」へ膨らむ。この仕組みの価値は
**ルールが少なく、1 件ずつが信用できる**ことにある。

## 手順

### 1. 候補を取る

**Issue の本文を原料にしないこと。** Issue は生成時点の描画であり、古い。
必ずスクリプトを叩き直す。

```bash
npm run harvest:rules -- --new-only   # 未検討のものだけ
npm run harvest:rules                 # 採用済み・却下済みの印付きで全件
```

`gh` の認証が要る。出力の各クラスタは次の形で出る。

```text
■ 🎯 Functional Correctness — apps/desktop  [3 件] 🆕 未検討
     PR#61 🟠 Major apps/desktop/src/renderer/style.css
   ✓ PR#60 🟠 Major apps/desktop/src/main/index.ts
```

行頭の `✓` が**修正実績あり**の印。これが差し引きの判定に効くので、後の手順で使う。

### 2. クラスタごとに、採用か却下かを提案する

利用者に丸投げせず、**各クラスタに推奨と理由を付けた表**を出す。
判断材料は `docs/guardrails.md` の 2 つ。

- **再発しているか。** 同じクラスの指摘が別の PR / 別のファイルで出ているなら採用寄り。
  同じ PR の同じファイルに 3 件並んでいるだけなら、それは 1 回の作業の指摘であって
  「このプロジェクトが構造上繰り返し踏む点」ではない。却下寄り。
- **次に同じ間違いが起きうるか。** 1 回きりの不具合修正はルールにしない。直して終わり。

強制手段は**判定可能性**で振り分ける。上に落とせるものを下に落とさない。

| 判定可能性                       | `enforcement` | 置き場所                              |
| -------------------------------- | ------------- | ------------------------------------- |
| 決定的に検査できる               | `test`        | `test/project-rules.test.mjs`         |
| 既存の linter が見る             | `lint`        | eslint 設定                           |
| 人の判断が要る                   | `doc`         | `.agents/rules/rules.md` の本文だけ   |

**ここで止まり、利用者の決定を待つ。** 提案した時点では何も書き換えない。

### 3a. 採用する — 編集は 3 箇所ある

1 箇所でも漏らすとメタテストが落ちるか、候補が毎回再提示される。

#### (1) `.agents/rules/rules.md` に追記する

ID は既存の最大値 + 1。`## RULE-\d+:` の形を崩さない（メタテストが読む）。

```markdown
## RULE-00X: （一行で言い切る要旨）

- **enforcement**: `test` / `lint` / `doc` のいずれか
- **出典**: PR#60 `apps/desktop/src/main/index.ts` / PR#60 `apps/desktop/src/renderer/renderer.js`

（なぜそれが問題になるのか。どう書くのが正しいのか。参照実装のパス。）
```

**出典の書式は厳密に守ること。** 収穫スクリプトはこれを
`/\*\*出典\*\*:([\s\S]*?)(?=\n\n)/` で読み、`PR#N` ごとにバッククォートのパスを結び付ける。
つまり次を満たす必要がある。

- `- **出典**:` で始まり、**空行で終わる**ブロックであること。
  途中に空行を挟むと、以降の出典が読まれない。
- パスは**バッククォートで囲む**こと。囲まないと 1 件も引かれない。
- PR 番号は `PR#60` の形。複数あるときは `PR#60 \`path\` / PR#63 \`path\`` と並べる。

**もっとも見落としやすい点**: 手順 1 の出力で `✓`（修正済み）が付いた項目を
**すべて** 出典に引くこと。1 件でも漏らすとそのクラスタは `new` のままになり、
採用したのに Issue へ出続ける。`statusOf` が
「修正実績のある指摘がすべて引かれているか」で採用済みを判定しているため。

#### (2) `AGENTS.md` のルール一覧表に行を足す

`AGENTS.md`（= `CLAUDE.md`）は Claude Code と Codex の両方が読む唯一の入口。
Codex は `@.agents/rules/rules.md` を展開しないので、この表が Codex 向けの唯一の手がかりになる。

```markdown
| RULE-00X | （要旨。正典の見出しと揃える）| test |
```

メタテストが `rules.md` の ID 集合と表の ID 集合の**両方向の一致**を検査する。
正典にあって表に無い、表にあって正典に無い、どちらも落ちる。

#### (3) 機械的に検査できるなら `test/project-rules.test.mjs` にテストを足す

`enforcement` が `test` なら必須。`doc` なら不要。

検査は **TypeScript の AST で書く**。正規表現で書かないこと。
文字列やコメントの中の `fetch(` を拾ってしまう。

ファイル名は**実際のパスを渡す**こと。TypeScript は拡張子から ScriptKind を決めるため、
`.tsx` を `.ts` として解析すると JSX の `<` が型アサーションと読まれ、木が壊れて
**何も検出しないまま緑になる**。

**判定は必ず違反側へ倒す。** 見逃しは緑になって気付けないが、誤検出は目に見えて直せる。

書いたら、**意図的に違反を注入して実際に落ちることを確認する**。
テストが緑であることは、検出器が正しいことを意味しない。何も検出しない検出器も緑になる。

### 3b. 却下する — `.agents/rules/declined.md` に 1 行記録する

```markdown
- `🎯 Functional Correctness | apps/desktop` — 却下理由（YYYY-MM-DD）
```

**クラスタのキーは手順 1 の出力からそのまま写すこと。打ち直さない。**
スクリプトは `/^-\s*` + バッククォート内の文字列で照合する。キーは
`カテゴリ | 領域` の形で、カテゴリには絵文字が含まれ、領域はパスの先頭 2 階層。
絵文字や空白が 1 文字違うだけで照合が外れ、却下したのに候補が出続ける。

理由は「なぜルールにしないか」を具体的に書く。「不要」では後から誰も判断を追えない。

### 4. 閉じたことを確認する — この手順を飛ばさない

編集したら、**収穫を叩き直して、扱ったクラスタが消えたことを確認する**。

```bash
npm run harvest:rules -- --new-only
```

扱ったクラスタがまだ `🆕 未検討` で出るなら、**出典の書式かクラスタのキーが間違っている**。
手順 3a(1) の「`✓` をすべて引く」か、手順 3b のキーの写し間違いを疑う。

`npm run test:project-rules` が緑であることは、この確認の代わりにならない。
別のものを見ているため。

最後に配線とメタテストを通す。

```bash
npm run test:project-rules      # ルール検査そのもの
npm run test:package-scripts    # AGENTS.md の表と正典の一致、出典の書式
```

### 5. Issue を閉じる

候補 Issue（`ルール候補: レビューで繰り返された指摘の棚卸し`）を扱ったら、
**何をどちらに倒したかをコメントしてから閉じる**。

```bash
gh issue comment <番号> --body "..."
gh issue close <番号>
```

全クラスタを倒しきっていないなら閉じない。残りをコメントに書いて開けておく。

## やってはいけないこと

- **利用者の決定を待たずに `rules.md` を書き換える。** 採否は人間が決める。
- **Issue の本文を原料にする。** 古い。必ずスクリプトを叩き直す。
- **却下を記録せずに「今回は見送り」で終える。** 次の push でまた出てくる。
  採らないことも決定であり、理由を残す。
- **判定できるものを markdown だけに書く。** markdown は助言、CI は強制。
- **候補を全部採用する。** ルールが増えるほど全体が読まれなくなる。
  guardrails.md の設計意図は「ルールを増やすこと」ではなく「守られるルールを持つこと」。
